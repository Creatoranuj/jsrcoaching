# Design Audit — 2026-09-18
Scope: src/pages, src/components, src/features (student, lesson player, course cards, chat, admin shells). Tokens read from src/index.css + tailwind.config.ts first.

## Baseline already solid (confirmed, not re-flagged)
- `tailwind.config.ts` sets `future: { hoverOnlyWhenSupported: true }` — sticky `hover:` in Capacitor WebView is already globally prevented (Linear/Stripe-grade discipline). No `hover:`-without-guard findings needed.
- `Button` (`src/components/ui/button.tsx`) bakes in `active:scale-[0.97]`, `duration-150 ease-out`, haptic taps per variant, and `min-h-11`/`h-11 w-11` icon size — tap targets ≥44px and press feedback are systemic, not per-instance.
- `Input`/`Textarea` already use `text-base` (with `md:text-sm` desktop-only downshift) — no iOS 16px-zoom risk.
- Shadows, radii base scale (`--radius` + `sm/md/lg` derivations) are centralized and consistent.

### [MEDIUM] [VIS] Hardcoded Tailwind palette colors instead of semantic success/gold tokens
**Where:** src/pages/AdminQuizManager.tsx:1015,1042 · src/pages/AdminFraudWatch.tsx:45,211 · src/pages/TeacherLiveView.tsx:194 · src/features/admin/components/AdminPaymentsTab.tsx:114,159 · src/components/admin/LibraryManager.tsx:675,681 · src/components/admin/ContentDrillDown.tsx:1174,1239,1246,1341
**Why it matters:** The app defines `--success` and `--gold` HSL tokens precisely so state colors survive dark-mode and future rebrands in one place — like Stripe Dashboard's semantic `--color-success` vs raw `green-600`. Raw `green-500/600/700`, `amber-500`, and an inline `bg-[hsl(38,92%,50%)]` bypass `.dark` theming entirely (they render identically in light/dark), producing contrast drift and an inconsistent "second brand color" the design system never approved.
**Fix:** Replaced with `bg-success`/`text-success`/`border-success` and `bg-gold`/`text-gold-foreground` equivalents, matching the destructive/primary pattern already used beside them.
**Status:** [APPLIED]

### [LOW] [A11Y] Sub-44px icon-only dismiss button in note upload row
**Where:** src/components/admin/LibraryManager.tsx:678-685 (was `h-6 text-red-500`)
**Why it matters:** A `h-6` (24px) tap target on a mobile-first admin upload flow fails the 44px minimum every other icon button in this file already respects (see `ContentDrillDown.tsx:1186-1194` using `h-9 w-9`). Apple HIG / Material both cite 44/48px as the floor; Linear's own icon buttons never go below 32px even on desktop-dense tables.
**Fix:** Bumped to `h-9 w-9` and swapped `text-red-500` → `text-destructive` to match the sibling delete buttons in the same admin surface.
**Status:** [APPLIED]

## Proposed (not applied — broader surface, needs product sign-off before a sweep)

### [LOW] [VIS] Scattered raw Tailwind color utilities across admin tab badges/chips
**Where:** src/features/admin/components/AdminUsersTab.tsx:41-78 (`bg-blue-50`, `text-blue-700`, `text-blue-500`), src/components/admin/ContentDrillDown.tsx:535-539 (`bg-blue-100 text-blue-700`, `bg-red-100 text-red-700` content-type chips), src/components/live/ZoomMeetingEmbed.tsx:168-169, src/pages/AdminCoursesTab.tsx:210-211 (`text-blue-500 hover:bg-blue-50`, `text-red-500 hover:bg-red-50`)
**Why it matters:** Same drift as the applied fixes above but spans ~30+ occurrences across admin-only screens; a category chip system like Notion's colored tags should map to a fixed token palette (`chart-1..5` already exist in tokens but are unused here) rather than ad hoc Tailwind swatches.
**Fix:** Introduce 2–3 additional semantic tokens (e.g. `--info`, mapped to existing `chart-1` blue) and do a scripted `s/blue-500|blue-600|blue-700/info/` sweep once a design sign-off names the mapping — left proposed because it touches ~15 files outside today's requested student-facing scope.
**Status:** [PROPOSED]

### [LOW] [VIS] Off-scale arbitrary radii on small UI atoms
**Where:** src/components/video/PdfSelectPopup.tsx:35 (`rounded-[3px]`), src/components/ui/chart.tsx:196,275 (`rounded-[2px]`), src/components/library/reader/MarkdownPreview.tsx:112 (`rounded-[4px]`)
**Why it matters:** The token scale is `sm = radius-4px`, `md = radius-2px`, `lg = radius`; arbitrary 2/3/4px values are pixel-hunted one-offs that won't track a future `--radius` rebrand, unlike Stripe's checkout UI where every radius — even tiny legend swatches — resolves through the same scale.
**Fix:** Swap to `rounded-sm` (resolves to `calc(0.75rem - 4px)` ≈ 8px — verify visually first since it's larger than the current 2–4px hairline swatches; if the tighter look is intentional for these thumbnail/legend chips, add a `--radius-xs: 2px` token instead of leaving raw arbitrary values). Left proposed pending a visual call on which resolution is intended.
**Status:** [PROPOSED]

### [LOW] [VIS] Full admin-auth screens (`AdminLogin.tsx`, `AdminRegister.tsx`) built entirely on literal `text-white`/`bg-white/10`/`border-white/20`
**Where:** src/pages/AdminLogin.tsx:81-134, src/pages/AdminRegister.tsx:83-134, src/pages/AdminUpload.tsx:808-824 (gradient header)
**Why it matters:** These screens paint a fixed dark gradient panel, so literal white text is arguably intentional (like a Stripe marketing-side login split-screen), but it means the screen never once resolves through `--foreground`/`--primary-foreground` and will silently diverge if the token palette shifts. Lower severity because it's isolated, decorative chrome, not a reusable component.
**Fix:** If the dark panel itself becomes a token (`--auth-panel-bg`), swap `text-white` → `text-primary-foreground` and `border-white/20` → `border-primary-foreground/20` for consistency; until then, flagging only, not touching per no-redesign / minimal-blast-radius rule for a page with heavy literal-color reliance.
**Status:** [PROPOSED]

### [LOW] [MOT] Group-hover video-lock overlays lack an active/press feedback path for touch
**Where:** src/pages/Course.tsx:94 (`opacity-0 hover:opacity-100`), src/pages/Dashboard.tsx:425 (`opacity-0 group-hover:opacity-100`)
**Why it matters:** With `hoverOnlyWhenSupported` these overlays correctly never get stuck visible on touch devices — but they also never *appear* on touch (no hover event fires), so a touch user gets zero visual affordance that the thumbnail is tappable/locked until they tap it, unlike Netflix/Lovable's course cards which show the lock/play glyph at rest on mobile breakpoints.
**Fix:** Add `max-md:opacity-100` (or a `[@media(pointer:coarse)]:opacity-100` variant) so the overlay is always visible on touch and only fades in on hover for pointer devices — a one-class addition per file, but held as proposed since it's a small visual behavior change on the course thumbnail grid warranting a screenshot check.
**Status:** [PROPOSED]

## Wins
- Global `hoverOnlyWhenSupported` future flag eliminates an entire class of Capacitor WebView sticky-hover bugs at the config level — most audits find this missing.
- Centralized `Button` primitive already encodes tap-target minimums, 150ms easing, `active:scale`, and per-variant haptics — exactly the "feel" checklist an app like this needs, done once instead of per-screen.
- Inputs already ship `text-base` to dodge iOS auto-zoom; no zoom-triggering `text-sm` inputs found anywhere in the codebase.
- Shadow and radius tokens are centralized CSS variables, not scattered arbitrary values, in the vast majority of screens.

## Rating: 4/5
Design-system plumbing (hover safety, tap targets, press states, zoom-safe inputs) is unusually mature for this size of codebase. The gaps found are cosmetic token-discipline lapses in admin-only surfaces (raw Tailwind swatches instead of `--success`/`--gold`/proposed `--info`), not structural or student-facing UX problems.
